GEMM All-Reduce Overlap Study

Where Ring All-Reduce time goes in MGPUSim, whether overlapping it with the GEMM pays off, and whether overlap changes the best work-group tile. This report replaces the two tile-tuning reports and the timing conclusions of the Ring-vs-Naive report, whose measurements predate the fixes in §1.

Author Hamed Alinezhad Lab HPCAN, Sharif University of Technology Code branch All-reduce @ f6a1df2 Platform MGPUSim v3.0.3 / Akita v3.0.0, R9 Nano (64 CUs), PCIe 4.0 ×16 Date 17 October 2026
Summary
  1. All-Reduce is slow because of per-launch overhead and slow kernels, not the link. Every kernel launch spends 22.75 µs on modeled host-to-device copies before it starts. A 1 MB All-Reduce on 2 GPUs spends 51% of its 1,068 µs there, and the link carries traffic for only 6% of the time.
  2. Larger All-Reduce chunks are the cheapest win. Raising the chunk from 64K to 256K elements makes a 1 MB All-Reduce on 2 GPUs 1.95× faster and a 4 MB one on 4 GPUs 2.6× faster, because each chunk costs a full round of launches.
  3. mccl's Ring All-Reduce ran every kernel on a single GPU. After the fix, link traffic matches the textbook ring volume exactly and 4-GPU All-Reduce is 1.10–1.65× faster.
  4. Overlap works, but one unbanded launch is still fastest. Overlapping band r's All-Reduce with band r+1's GEMM cuts the window by 10–34% compared with the same bands run back to back. Every extra band is a complete extra All-Reduce, though, and that costs more than overlap hides at these shapes.
  5. The best tile follows band size, not overlap. With one band, 16×16 work-groups win; with 128- or 64-row bands, 4×4 wins, with or without overlap. The margins are 1–14%.
  6. Open issue: two 4-GPU overlapped runs produced wrong results (§4). Overlap results on 4 GPUs need that resolved before they are trusted.

2. Where All-Reduce time goes

The link is idle most of the time. Ring All-Reduce cost is a fixed price per kernel launch plus kernels that move data far below link speed.

allreducebench runs one All-Reduce per message size and chunk size on fresh data, and traces three things during it: the driver's host-to-device copies, any push or reduce kernel executing on a GPU, and remote requests arriving at each GPU's RDMA engine (with their bytes). "Other" is the remainder.

A fixed cost per launch

For each chunk, the ring runs 3(G−1) steps with one kernel launch per GPU per step: 6 launches on 2 GPUs and 36 on 4. Before each launch the driver queues three host-to-device copies (the code object, the kernel arguments and the dispatch packet), and models each with a fixed latency of 14,500 driver cycles (WithH2DCycles(14500) in samples/runner/timingplatform.go). Measured, that comes to 22.75 µs per launch, so the setup copies take 136.5 µs per chunk on 2 GPUs and 410 µs per chunk on 4 GPUs, whatever the message size.

A real runtime loads a code object once and writes kernel arguments through mapped memory, so this cost comes from the simulator's driver model rather than from the hardware it models. Conclusions that hinge on it, such as how many bands are affordable, may not carry over to real GPUs.

The kernels, not the link, set the speed of data movement

Once chunks are large, kernel time dominates. A 4 MB All-Reduce on 4 GPUs with 1M-element chunks moves 24 MB across the links in 3,682 µs: about 6.8 GB/s in aggregate, against 34.4 GB/s for each of the four PCIe 4.0 ×16 links. Remote traffic is in flight for only 1,362 µs of the 3,267 µs the kernels run. The push and reduce kernels use a fixed 1,024 threads (16 work-groups of 64), and each thread moves one 4-byte element per loop iteration, so they are latency-bound.

The GEMM benchmark exposes this as -allreduce-chunk (default 65,536 elements). None of the sweeps in §3 depend on it: a 256×256 result is exactly one 64K-element chunk.

Effect of the mccl fix

Before the fix, the kernels ran on one GPU, and remote reads made up most of the link traffic. After it, remote reads drop to zero and remote writes equal the ring's 2(G−1)·S exactly: 2 MB for a 1 MB message on 2 GPUs, 6 MB on 4. On 4 GPUs the fix makes All-Reduce 1.10–1.65× faster. On 2 GPUs it is unchanged for small messages and up to 15% slower for large ones: the ring now moves data with remote stores, and in this model those cost more than the one-GPU version's remote loads. The full before-and-after table is in the appendix.

3. Tile size, bands and overlap

The question: once All-Reduce of band r overlaps with the GEMM of band r+1, does the best work-group tile change?

The kernel computes a fixed 4×4 output micro-tile per work-item, so a T×T work-group produces a 4T×4T output tile: tileSize 4, 8 and 16 mean 16×16, 32×32 and 64×64 output tiles. 32 is infeasible (74 VGPRs per work-item caps a CU at 12 wavefronts). M is split into bands of 128 or 64 rows, or left whole. Each band is its own GEMM launch and its own All-Reduce of rows×N floats, run either back to back (sequential) or overlapped. All runs use Ring All-Reduce with the fixed mccl.

The shapes keep M and N small and grow K, so GEMM and All-Reduce cost about the same. The one-band runs at tile 8 show how close each shape gets:

One band is fastest in every shape

Each extra band is a complete ring All-Reduce with its fixed launch cost. On 256×256×1024 with 2 GPUs, All-Reduce time grows from 255 to 379 to 659 µs for 1, 2 and 4 bands, while the bytes moved stay the same. Banding also makes the GEMM slower: each band is a separate launch with fewer work-groups, and tile-8 GEMM time grows from 266 to 424 to 764 µs.

Overlap hides most of what banding adds to the GEMM

Against the same bands run back to back, overlap shortens the window by 22% (128-row bands) and 34% (64-row bands) on 256×256×1024, 16% on 256×256×4096 with 4 GPUs, and 10–15% on the GEMM-heavy shape. With 64-row bands on 256×256×1024, exposed GEMM time drops from 747 to 263 µs, back to about the one-band GEMM time. All-Reduce time is the same with or without overlap (659 vs 662 µs), so a GEMM running alongside does not slow the collective. What overlap cannot recover is the extra All-Reduce cost of having more bands.

The best tile does change, but banding changes it, not overlap: sequential and overlapped runs at the same band size pick the same tile. The likely reason is parallelism per launch. A 256-wide output gives 16×16 work-groups only 16 work-groups per GPU on 64 CUs for the whole matrix, and a 64-row band at tileSize 16 is only 4. Smaller tiles keep more CUs busy in short launches. The effect is small at the balanced shapes (1–3%) and largest on the GEMM-heavy one (8–14%). It is also biased toward large tiles, because MGPUSim does not count LDS against occupancy (§4).

A lead from the 512³ sweep

The 512³ sweep ran before the mccl fix, so its All-Reduce numbers come from the one-GPU behavior and are only a reference. It still points to when overlap can win. At N = 512 a whole-matrix All-Reduce is already split into four 64K-element chunks, so 128- and 256-row bands add no All-Reduce steps (All-Reduce stays at about 1,004 µs). There, overlapped 128-row bands beat one band: 1,167 vs 1,196 µs at tileSize 8, and 1,180 vs 1,470 µs at tileSize 4. Overlap pays off when band boundaries line up with chunks the All-Reduce would make anyway. That is worth rerunning on the fixed mccl (§5).

4. Validity and open issues

Open issue

Two 4-GPU overlapped runs fail verification. At 256×256×4096 on 4 GPUs with 64-row bands and overlap, tileSize 4 and 8 produce values about twice the expected sum (first mismatch at C[96,16]: 2,045.5 vs 1,027.8). The same configurations pass without overlap, at tileSize 16, and on 2 GPUs. The cause is not established. No cache flush or invalidation happens between the All-Reduce kernels: kernel launches never invalidate L1 in this driver, which only flushes on a host copy to a buffer it has marked dirty. A stale scratch buffer, reused across bands and read through a remote GPU's L1, would fit the symptom, but that is not confirmed. Until it is resolved, treat overlapped 4-GPU results as provisional; the verified ones in this report did pass the full CPU check.

  • The driver's launch model sets the price of banding. The 22.75 µs per launch comes from a fixed modeled copy latency, three copies per launch (§2). Results that trade launches for overlap depend on that constant.
  • LDS does not limit occupancy in the simulator. MGPUSim's resource check reads WGGroupSegmentByteSize, which is 0 for this kernel, so tileSize 16's 16 KB of LDS per work-group costs nothing. On hardware with 64 KB of LDS per CU it would cap residency at four work-groups. Large tiles are favored.
  • The kernel is a patched binary. The fix to mmmKernel_local is a binary patch of the upstream code object, because MGPUSim v3 loads code object v2 and current LLVM no longer emits it. All other instructions match upstream, so timing stays comparable with earlier runs.
  • Phase timers read simulated time from the host side, after each blocking call returns. They split the window; they don't trace individual kernels.
  • Scope. One GEMM kernel, three shapes, Ring All-Reduce only, default R9 Nano configuration. The 512³ sweep is pre-fix and covers only 2 GPUs fully (3 of its 4-GPU runs finished).

5. Next steps

  1. Find the cause of the 4-GPU overlap failure; check L1 invalidation between collective kernels first.
  2. Rerun a 512-wide shape on the fixed mccl with band sizes that line up with All-Reduce chunks. That is where overlap is expected to beat one band.
  3. Tie band size to chunk size (one chunk per band), so the tile and band choice also sets the All-Reduce message size.
  4. Test how sensitive the conclusions are to the driver's per-copy latency, for example by halving WithH2DCycles, before reading them as hardware results.

6. Reproducing the results

From the workspace root, on branch All-reduce. Raw outputs land in results/; each sweep resumes where it stopped.

# All-Reduce breakdown (fixed mccl)
cd simulator/mgpusim-3.0.3 && go build -o allreducebench ./samples/allreducebench
./allreducebench -ring-gpus 2 -out g2.csv     # and -ring-gpus 4

# Tile x band x overlap sweeps
python3 scripts/sweep_overlap.py --m 256 --k 1024 --n 256 --gpus 2 \
    --tiles 16,8,4 --bands 0,128,64 --outdir results/overlap_sweep_k1024
python3 scripts/sweep_overlap.py --m 256 --k 4096 --n 256 --gpus 4,2 \
    --tiles 16,8,4 --bands 0,128,64 --outdir results/overlap_sweep_k4096

# Everything above, detached and resumable
scripts/run_pending_experiments.sh
