§1 Summary

Ring All-Reduce wins everywhere tested — and the workload is communication-bound, not compute-bound

Across every problem size and GPU count tested, Ring All-Reduce beat the naive centralized (gather–reduce–broadcast) baseline, with the gap widening as problem size grows — from 3% at 128³ up to 23% at 512³ on 4 GPUs. But the more consequential finding came from timing the compute and communication phases separately: for a 256³ matrix on 2 GPUs, All-Reduce communication and driver overhead account for ~59% of total execution time, more than the GEMM kernel itself. Cache capacity barely moves that number; DRAM capacity does, but through reduced rank-level parallelism inflating memory latency, not through spilling a working set.

Three genuine bugs in the underlying simulator were found and worked around along the way — a broken kernel-offset parameter, a command-queue draining deadlock, and a DRAM-controller crash at small rank counts. They're documented in §6 since they shape how the benchmark code had to be written and would resurface for anyone else building on the same kernel.

§2 What was built

Naive All-Reduce, a K-split GEMM benchmark, and two framework knobs that didn't exist before

Naive All-Reduce (benchmarks/mccl/allreduce_naive.go) implements centralized gather–reduce–broadcast alongside the existing Ring implementation: every non-root GPU pushes its chunk directly to a root, which reduces sequentially and pushes the final result back out directly — no intermediate hops, so the root's link bandwidth is the bottleneck as GPU count grows. It reuses the existing push/reduce GCN3 kernels and matches AllReduceRing's signature exactly.

The distributed GEMM benchmark (benchmarks/allreducegemm) splits the K (contraction) dimension evenly across GPUs. Each GPU computes a full-size M×N partial product from its own private K-slice of A and B, and All-Reduce sums the partials into the final result — making All-Reduce the actual synchronization primitive, rather than a benchmark that merely gathers disjoint output tiles.

Two runner-level knobs that the sensitivity sweep in §5 needed didn't exist before this work: an L1 cache size flag, and a DRAM size flag that turned out to be silently disconnected — WithDRAMSize() was a real builder method, but the DRAM controller ignored it and hardcoded 4GB regardless. Both are now wired through to the CLI as -l1-cache-size and -dram-size, alongside the pre-existing -l2-cache-size.

Why L1 hit rate reads 0% at every size

The reused GCN3 kernel caches its A-matrix tile in explicit local (shared) memory rather than relying on the hardware L1 — so L1 sees a pure streaming access pattern with no reuse for automatic caching to exploit, and its hit rate is flat at 0% from 8KB to 32KB. Execution time correspondingly doesn't move (±1.6%, within simulation noise). L2, which sits below the point where the kernel's own tiling already captures reuse, is more informative: shrinking it to 512KB drops the hit rate from 83.9% to 75.6% and measurably slows the run.

Why DRAM=2GB is 22% slower despite a higher L2 hit rate

Restricting DRAM from 4GB to 2GB doesn't shrink the working set below what fits — L2 hit rate actually rises slightly (83.9% → 87.0%). The slowdown comes from the DRAM controller side: available capacity is split across a fixed 16 memory banks, and at 2GB the resulting rank count gives the controller less internal parallelism to hide access latency. Average L1 request latency roughly triples (1.06×10&supminus;&sup5;s → 3.14×10&supminus;&sup5;s), and that shows up directly in the GEMM kernel's own time, not in the AllReduce phase — see §5.

§5 Where the time actually goes

Communication, not computation, dominates at these problem sizes

The communication-plus-overhead figure is essentially constant across every L1/L2/DRAM variant — it doesn't depend on the memory hierarchy, because it's dominated by All-Reduce message passing and command-queue bookkeeping rather than memory access. The kernel time is what moves: restricting DRAM to 2GB inflates compute time by 53% (413μs → 633μs) through the rank-parallelism effect in §4, which is also why that configuration is the only one where communication drops below half the total — not because communication got faster, but because compute got slower.

What this means for the §3 scaling numbers

At 256³ and 2 GPUs, roughly 59 cents of every simulated second is spent on All-Reduce and driver overhead before a single extra FLOP of parallel compute is realized. Splitting K further across more GPUs shrinks the 41-cent compute share while the AllReduce volume (proportional to the full M×N result, not to K) grows with GPU count instead of shrinking. That is precisely the mechanism behind the falling efficiency numbers in §3: this benchmark, at these sizes, is communication-bound, and no amount of GPU-count scaling fixes a communication-bound workload — it makes it worse.

§6 Appendix

Three simulator bugs found along the way

None of these are bugs in the code delivered here — they're pre-existing issues in MGPUSim/Akita that this benchmark's usage pattern happened to trigger. Each is worked around in allreducegemm's implementation; documenting them here so the workarounds don't look arbitrary, and so they don't have to be rediscovered.

Bug 1 · Broken kernel Y-offset parameter

The reused AMD APP SDK matmul kernel's HiddenGlobalOffsetY parameter, used by the existing multi-GPU row-split code path to target a sub-region of the output, does not work: a single-workgroup launch with a nonzero Y offset silently writes zeros, and any grid with more than one workgroup-row in Y corrupts most of the output (75% of a 128×128 result was wrong, confirmed independently of this benchmark's own code). Worked around by never using the offset parameter — instead computing each 32-row band's target address directly via pointer arithmetic on MatrixA/MatrixC, with every individual launch kept to a single workgroup-row.

Bug 2 · Driver hang with multiple undrained queues

Issuing several kernel launches on one GPU's command queue while other GPUs also have undrained work outstanding can hang DrainCommandQueue indefinitely — reproduced with as little as 2 queued launches per GPU across 4 GPUs, independent of All-Reduce. Worked around by issuing launches round-robin across GPUs, one band per GPU per round, draining every GPU's queue together before starting the next round — never letting more than one launch sit undrained on any single queue.

Bug 3 · DRAM controller crash at small rank counts

Setting DRAM size to 1GB (vs. the 4GB default) crashes the DRAM controller with an out-of-range index, apparently because the resulting rank count computes to a degenerate value. 2GB works. The §4 sweep uses 2GB as its "restricted" configuration for this reason; true low-capacity behavior below whatever threshold triggers this remains unobserved.
