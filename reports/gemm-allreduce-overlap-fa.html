مطالعهٔ Overlap در GEMM و All-Reduce

زمانِ Ring All-Reduce در MGPUSim صرف چه می‌شود، آیا overlap کردنِ آن با GEMM می‌ارزد، و آیا overlap بهترین tile را عوض می‌کند. این گزارش جایگزین دو گزارشِ tile tuning و نتیجه‌گیری‌های زمانیِ گزارشِ Ring-vs-Naive است؛ اندازه‌گیری‌های آن گزارش‌ها پیش از اصلاح‌های بخش ۱ انجام شده بود. نسخهٔ انگلیسی

نویسنده حامد علی‌نژاد آزمایشگاه HPCAN، دانشگاه صنعتی شریف کد branch All-reduce @ f6a1df2 پلتفرم MGPUSim v3.0.3 / Akita v3.0.0، R9 Nano (۶۴ CU)، PCIe 4.0 ×16 تاریخ ۲۵ مهر ۱۴۰۵
خلاصه
  1. کندیِ All-Reduce از سربارِ هر kernel launch و kernelهای کند است، نه از link. پیش از هر kernel launch، 22.75 µs صرفِ host-to-device copyهای مدل‌شده می‌شود. یک All-Reduce یک‌مگابایتی روی ۲ GPU، 51% از 1,068 µs زمانش را همین‌جا می‌گذراند و link فقط 6% از زمان ترافیک دارد.
  2. بزرگ‌تر کردنِ chunk ارزان‌ترین بهبود است. بردنِ chunk از 64K به 256K عنصر، All-Reduce یک‌مگابایتی روی ۲ GPU را 1.95× و All-Reduce چهارمگابایتی روی ۴ GPU را 2.6× سریع‌تر می‌کند، چون هر chunk یک دورِ کامل kernel launch دارد.
  3. Ring All-Reduce در mccl همهٔ kernelهایش را روی یک GPU اجرا می‌کرد. بعد از اصلاح، ترافیکِ link دقیقاً برابرِ حجمِ نظریِ ring است و All-Reduce روی ۴ GPU بین 1.10× تا 1.65× سریع‌تر شده است.
  4. Overlap کار می‌کند، اما هنوز یک launch بدونِ band سریع‌ترین است. Overlap کردنِ All-Reduce مربوط به band r با GEMM مربوط به band r+1، زمانِ window را نسبت به اجرای پشت‌سرهمِ همان bandها 10–34% کم می‌کند؛ اما هر band اضافه یعنی یک All-Reduce کاملِ اضافه، و در این shapeها هزینه‌اش از چیزی که overlap پنهان می‌کند بیشتر است.
  5. بهترین tile تابعِ اندازهٔ band است، نه overlap. با یک band، work-groupهای 16×16 بهترین‌اند؛ با bandهای ۱۲۸ یا ۶۴ سطری، 4×4 برنده است، چه با overlap چه بدونِ آن. اختلاف‌ها بین 1% تا 14% است.
  6. مسئلهٔ باز: دو اجرای overlap روی ۴ GPU نتیجهٔ غلط دادند (بخش ۴). تا این مشکل حل نشود، نتایجِ overlap روی ۴ GPU قابل اعتماد نیستند.

۱. از گزارش‌های قبلی چه تغییر کرده

سه باگ روی همهٔ اندازه‌گیری‌های قبلی اثر گذاشته بود. هر سه در branch All-reduce اصلاح شده‌اند و گزارش‌های قدیمی حالا یادداشتِ «outdated» دارند.

مشکلاثر روی نتایجِ قبلیاصلاح
kernelِ mmmKernel_local (برگرفته از AMD APP SDK) ماتریس A را با Y idِ local (lIdY) اندیس‌گذاری می‌کرد، پس هر ردیفِ work-group بعد از اولی، سطرهای اشتباهِ A را می‌خواند. benchmark در هر kernel فقط یک ردیفِ work-group اجرا می‌کرد، پس tile size تعدادِ launchها را هم تعیین می‌کرد (۱۶ / ۸ / ۴ launch برای هر GPU در 256³). رتبه‌بندیِ قبلیِ tileها به همان اندازه که tiling را می‌سنجید، سربارِ launch را هم می‌سنجید. patch باینریِ پنج‌دستوری روی kernelِ موجود (benchmarks/allreducegemm/native/patch_gidy.py)؛ حالا یک launch کلِ M را پوشش می‌دهد. commit 3be1037.
tune_gemm_tile.py بدونِ توجه به --gpus همیشه -gpus=1,2 می‌فرستاد. همهٔ sweepهای tile روی ۲ GPU اجرا شده بودند. لیستِ GPUها از --gpus ساخته می‌شود. commit 3be1037.
mccl، command queueِ هر communicator را بدونِ select کردنِ GPUِ آن می‌ساخت، در حالی که هر queue به GPUِ انتخاب‌شدهٔ فعلیِ context متصل می‌شود. همهٔ kernelهای push و reduce در Ring All-Reduce (و Ring Broadcast) روی آخرین GPUِ انتخاب‌شده اجرا می‌شدند و حافظهٔ GPUهای دیگر را از طریقِ RDMA می‌خواندند و می‌نوشتند. نتیجه‌ها درست بود، برای همین هیچ testی آن را نگرفت. select کردنِ هر GPU پیش از ساختنِ queueِ آن (benchmarks/mccl/allreduce.go). commit 141ff40. زمان‌بندیِ DNN trainerهایی که از mccl استفاده می‌کنند هم تغییر می‌کند.

ابزارهای جدیدی که در ادامه استفاده شده‌اند: benchmark حالا یک phase split از زمانِ شبیه‌سازی‌شده بینِ اولین GEMM launch و پایانِ آخرین All-Reduce (که اینجا window نامیده می‌شود) گزارش می‌کند: زمانی که host منتظرِ تمام شدنِ GEMM است، و زمانی که داخلِ فراخوانی‌های All-Reduce می‌گذرد. samples/allreducebench فقط Ring All-Reduce را اجرا می‌کند و ردیابی می‌کند زمانِ هر فراخوانی کجا صرف می‌شود. scripts/sweep_overlap.py گریدهای tile × band × overlap را اجرا می‌کند، و نتیجهٔ همهٔ اجراهای این گزارش با یک CPU reference چک (verify) شده است.

۲. زمانِ All-Reduce کجا می‌رود

link بیشترِ وقت بیکار است. هزینهٔ Ring All-Reduce یک قیمتِ ثابت به ازای هر kernel launch است، به‌علاوهٔ kernelهایی که داده را خیلی کندتر از سرعتِ link جابه‌جا می‌کنند.

allreducebench برای هر اندازهٔ پیام و هر اندازهٔ chunk یک All-Reduce روی دادهٔ تازه اجرا می‌کند و سه چیز را ردیابی می‌کند: host-to-device copyهای driver، هر kernelِ push یا reduce که روی یک GPU در حال اجراست، و درخواست‌های remote که به RDMA engineِ هر GPU می‌رسند (همراه با تعداد بایت‌ها). «Other» باقی‌ماندهٔ زمان است.

یک هزینهٔ ثابت به ازای هر launch

برای هر chunk، ring به تعدادِ 3(G−1) گام اجرا می‌شود و در هر گام روی هر GPU یک kernel launch دارد: ۶ launch روی ۲ GPU و ۳۶ launch روی ۴ GPU. پیش از هر launch، driver سه host-to-device copy در صف می‌گذارد (code object، kernel arguments و dispatch packet) و هر کدام را با یک latency ثابتِ ۱۴٬۵۰۰ سیکلِ driver مدل می‌کند (WithH2DCycles(14500) در samples/runner/timingplatform.go). در اندازه‌گیری، این می‌شود 22.75 µs برای هر launch؛ یعنی setup copyها برای هر chunk روی ۲ GPU 136.5 µs و روی ۴ GPU 410 µs طول می‌کشند، مستقل از اندازهٔ پیام.

یک runtimeِ واقعی code object را فقط یک بار بارگذاری می‌کند و kernel argumentها را از طریقِ mapped memory می‌نویسد. پس این هزینه از مدلِ driver در شبیه‌ساز می‌آید، نه از سخت‌افزاری که مدل می‌شود. نتیجه‌هایی که به آن وابسته‌اند، مثلاً اینکه چند band به‌صرفه است، ممکن است روی GPUِ واقعی صدق نکنند.

سرعتِ جابه‌جاییِ داده را kernelها تعیین می‌کنند، نه link

وقتی chunkها بزرگ باشند، زمانِ kernel غالب است. یک All-Reduce چهارمگابایتی روی ۴ GPU با chunkهای 1M، در 3,682 µs حدودِ 24 MB را از روی linkها جابه‌جا می‌کند: در مجموع حدودِ 6.8 GB/s، در حالی که هر کدام از چهار link از نوعِ PCIe 4.0 ×16 ظرفیتِ 34.4 GB/s دارد. ترافیکِ remote فقط در 1,362 µs از 3,267 µs اجرای kernelها در جریان است. kernelهای push و reduce تعدادِ ثابتِ ۱٬۰۲۴ thread دارند (۱۶ work-groupِ ۶۴تایی) و هر thread در هر دورِ حلقه فقط یک عنصرِ ۴ بایتی جابه‌جا می‌کند، پس latency-bound هستند.

اثرِ اصلاحِ mccl

پیش از اصلاح، kernelها روی یک GPU اجرا می‌شدند و بیشترِ ترافیکِ link را remote readها تشکیل می‌دادند. بعد از اصلاح، remote readها صفر می‌شوند و remote writeها دقیقاً برابرِ 2(G−1)·S هستند: ۲ مگابایت برای پیامِ ۱ مگابایتی روی ۲ GPU، و ۶ مگابایت روی ۴ GPU. روی ۴ GPU، این اصلاح All-Reduce را 1.10× تا 1.65× سریع‌تر می‌کند. روی ۲ GPU برای پیام‌های کوچک تغییری ندارد و برای پیام‌های بزرگ تا 15% کندتر است: ring حالا داده را با remote store جابه‌جا می‌کند، و در این مدل هزینهٔ آن از remote loadهای نسخهٔ تک‌GPU بیشتر است. جدولِ کاملِ قبل و بعد در پیوست آمده است.

۳. اندازهٔ tile، bandها و overlap

سؤال: وقتی All-Reduce مربوط به band r با GEMM مربوط به band r+1 overlap شود، آیا بهترین work-group tile عوض می‌شود؟

kernel برای هر work-item یک micro-tileِ خروجیِ ثابتِ 4×4 حساب می‌کند، پس یک work-groupِ T×T یک tileِ خروجیِ 4T×4T می‌سازد: tileSize 4، 8 و 16 یعنی tileهای خروجیِ 16×16، 32×32 و 64×64. مقدارِ ۳۲ امکان‌پذیر نیست (۷۴ VGPR برای هر work-item، هر CU را به ۱۲ wavefront محدود می‌کند).

band چیست؟ یک band نواری افقی از سطرهای ماتریسِ خروجیِ C است. هر GPU یک C جزئیِ کامل (M×N) از برشِ K خودش حساب می‌کند و All-Reduce این C های جزئی را جمع می‌زند. به‌جای اینکه کلِ C یک‌جا محاسبه و reduce شود، M به bandهای ۱۲۸ یا ۶۴ سطری تقسیم می‌شود (یا دست‌نخورده می‌ماند). هر band یک GEMM launchِ جدا و یک All-Reduceِ جدا روی rows×N عنصر دارد، که یا پشت‌سرهم اجرا می‌شوند (sequential) یا با overlap. bandها سطرهای متفاوتی از C را می‌نویسند، برای همین GEMMِ یک band و All-Reduceِ band قبلی می‌توانند هم‌زمان اجرا شوند. همهٔ اجراها از Ring All-Reduce با mccl اصلاح‌شده استفاده می‌کنند.

در این shapeها M و N کوچک نگه داشته شده‌اند و K بزرگ شده، تا هزینهٔ GEMM و All-Reduce به هم نزدیک باشد. اجراهای یک‌bandی با tileSize 8 نشان می‌دهند هر shape چقدر به این تعادل نزدیک است:

در همهٔ shapeها یک band سریع‌ترین است

هر band اضافه یک ring All-Reduceِ کامل با هزینهٔ ثابتِ launchهای خودش است. در 256×256×1024 روی ۲ GPU، زمانِ All-Reduce برای ۱، ۲ و ۴ band از 255 به 379 و بعد 659 µs می‌رسد، در حالی که حجمِ داده ثابت است. band کردن GEMM را هم کندتر می‌کند: هر band یک launchِ جدا با work-groupهای کمتر است، و زمانِ GEMM با tileSize 8 از 266 به 424 و 764 µs می‌رسد.

overlap بیشترِ چیزی را که band به GEMM اضافه می‌کند پنهان می‌کند

در مقایسه با اجرای پشت‌سرهمِ همان bandها، overlap زمانِ window را در 256×256×1024 به اندازهٔ 22% (bandهای ۱۲۸ سطری) و 34% (bandهای ۶۴ سطری)، در 256×256×4096 با ۴ GPU به اندازهٔ 16%، و در shapeِ GEMM-heavy بین 10% تا 15% کم می‌کند. با bandهای ۶۴ سطری در 256×256×1024، زمانِ پنهان‌نشدهٔ GEMM از 747 به 263 µs می‌رسد، یعنی تقریباً همان زمانِ GEMMِ یک‌bandی. زمانِ All-Reduce با و بدونِ overlap یکسان است (659 در برابرِ 662 µs)، پس GEMMِ هم‌زمان collective را کند نمی‌کند. چیزی که overlap نمی‌تواند جبران کند، هزینهٔ All-Reduceهای اضافه‌ای است که از band بیشتر می‌آید.

بهترین tile عوض می‌شود، اما عاملش band است، نه overlap: اجراهای sequential و overlap با اندازهٔ band یکسان، tileِ یکسانی را انتخاب می‌کنند. دلیلِ محتمل، میزانِ موازی‌سازی در هر launch است. خروجیِ ۲۵۶ستونی برای کلِ ماتریس فقط ۱۶ work-groupِ 16×16 روی ۶۴ CUِ هر GPU می‌دهد، و یک bandِ ۶۴ سطری با tileSize 16 فقط ۴ work-group دارد. tileهای کوچک‌تر در launchهای کوتاه CUهای بیشتری را مشغول نگه می‌دارند. این اثر در shapeهای متعادل کوچک است (1–3%) و در shapeِ GEMM-heavy بیشترین مقدار را دارد (8–14%). همچنین به نفعِ tileهای بزرگ سوگیری دارد، چون MGPUSim مصرفِ LDS را در occupancy حساب نمی‌کند (بخش ۴).

یک سرنخ از sweepِ 512³

sweepِ 512³ پیش از اصلاحِ mccl اجرا شد، پس اعدادِ All-Reduce در آن از حالتِ تک‌GPU می‌آیند و فقط مرجع هستند. با این حال نشان می‌دهد overlap کِی می‌تواند برنده شود. در N = 512، All-Reduceِ کلِ ماتریس از قبل به چهار chunkِ 64K عنصری تقسیم می‌شود، پس bandهای ۱۲۸ و ۲۵۶ سطری هیچ گامِ All-Reduceِ اضافه‌ای نمی‌سازند (All-Reduce حدودِ 1,004 µs باقی می‌ماند). آنجا bandهای ۱۲۸ سطری با overlap از یک band سریع‌تر بودند: 1,167 در برابرِ 1,196 µs با tileSize 8، و 1,180 در برابرِ 1,470 µs با tileSize 4. overlap وقتی سود می‌دهد که مرزِ bandها بر chunkهایی منطبق باشد که All-Reduce در هر حال می‌سازد. این آزمایش ارزشِ تکرار با mccl اصلاح‌شده را دارد (بخش ۵).

۴. اعتبارِ نتایج و مسائلِ باز

مسئلهٔ باز

دو اجرای overlap روی ۴ GPU در verify رد می‌شوند. در 256×256×4096 روی ۴ GPU با bandهای ۶۴ سطری و overlap، tileSizeهای 4 و 8 مقادیری حدوداً دو برابرِ جمعِ مورد انتظار تولید می‌کنند (اولین mismatch در C[96,16]: 2,045.5 به‌جای 1,027.8). همین پیکربندی‌ها بدونِ overlap، با tileSize 16 و روی ۲ GPU درست هستند. علت هنوز مشخص نیست. بینِ kernelهای All-Reduce هیچ cache flush یا invalidationی رخ نمی‌دهد: در این driver، kernel launch هیچ‌وقت L1 را invalidate نمی‌کند و flush فقط هنگامِ host copy به bufferی رخ می‌دهد که dirty علامت خورده باشد. یک scratch bufferِ کهنه (stale) که بینِ bandها دوباره استفاده می‌شود و از طریقِ L1ِ یک GPUِ دیگر خوانده می‌شود با این علامت‌ها جور درمی‌آید، اما تأیید نشده است. تا حلِ این مشکل، نتایجِ overlap روی ۴ GPU را موقت بدانید؛ اجراهای verify‌شدهٔ این گزارش از چکِ کاملِ CPU گذشته‌اند.

  • مدلِ launch در driver قیمتِ band را تعیین می‌کند. ۲۲٫۷۵ میکروثانیه برای هر launch از یک latencyِ ثابتِ مدل‌شده برای copy می‌آید، سه copy برای هر launch (بخش ۲). نتیجه‌هایی که launch را با overlap معاوضه می‌کنند به این ثابت وابسته‌اند.
  • LDS در شبیه‌ساز occupancy را محدود نمی‌کند. بررسیِ منابع در MGPUSim مقدارِ WGGroupSegmentByteSize را می‌خواند که برای این kernel صفر است، پس ۱۶ کیلوبایت LDS برای هر work-group در tileSize 16 هزینه‌ای ندارد. روی سخت‌افزاری با ۶۴ کیلوبایت LDS برای هر CU، این مقدار تعدادِ work-groupهای مقیم را به چهار محدود می‌کرد. نتایج به نفعِ tileهای بزرگ سوگیری دارند.
  • kernel یک باینریِ patch‌شده است. اصلاحِ mmmKernel_local یک patchِ باینری روی code objectِ اصلی است، چون MGPUSim v3 فقط code object v2 را بارگذاری می‌کند و LLVMِ فعلی دیگر آن را تولید نمی‌کند. بقیهٔ دستورها با نسخهٔ اصلی یکسان‌اند، پس زمان‌بندی با اجراهای قبلی قابل مقایسه می‌ماند.
  • phase timerها زمانِ شبیه‌سازی را از سمتِ host می‌خوانند، بعد از برگشتنِ هر فراخوانیِ blocking. آن‌ها window را تقسیم می‌کنند، اما kernelهای تکی را ردیابی نمی‌کنند.
  • دامنه. یک kernelِ GEMM، سه shape، فقط Ring All-Reduce، و پیکربندیِ پیش‌فرضِ R9 Nano. sweepِ 512³ پیش از اصلاح است و فقط برای ۲ GPU کامل است (۳ اجرا از اجراهای ۴ GPU تمام شد).

۵. گام‌های بعدی

  1. پیدا کردنِ علتِ خطای overlap روی ۴ GPU؛ اول invalidationِ L1 بینِ kernelهای collective بررسی شود.
  2. تکرارِ یک shapeِ ۵۱۲ستونی با mccl اصلاح‌شده، با اندازه‌های bandی که بر chunkهای All-Reduce منطبق‌اند. انتظار می‌رود آنجا overlap از یک band بهتر باشد.
  3. گره زدنِ اندازهٔ band به اندازهٔ chunk (یک chunk برای هر band)، تا انتخابِ tile و band اندازهٔ پیامِ All-Reduce را هم تعیین کند.
  4. سنجیدنِ حساسیتِ نتیجه‌ها به latencyِ هر copy در driver، مثلاً با نصف کردنِ WithH2DCycles، پیش از اینکه آن‌ها را نتیجهٔ سخت‌افزاری بدانیم.
