GEMM Work-Group Tile Size Tuning

Evaluation of the tune_gemm_tile.py test harness, isolating the impact of work-group dimension scaling, code execution efficiency, and microarchitectural bottlenecks[cite: 1].

Simulator: MGPUSim v3 / Akita v3[cite: 1]
GPU model: 2× R9 Nano · 64 CU/GPU[cite: 1]
Dimensions: M=256, K=256, N=256[cite: 1]
Algorithm: Ring All-Reduce[cite: 1]

The 16×16 configuration is 2.3× faster than baseline

Increasing the work-group tile size drastically reduces both kernel execution overhead and end-to-end total time[cite: 1]. Running the tuning script revealed that the 16×16 configuration maximizes data reuse within the L1/Vector Data Caches, operating 2.32× faster than the 4×4 layout[cite: 1].

However, analysis of the simulator code reveals that these scaling results are heavily influenced by kernel dispatch overhead and physical register constraints, which limit the upper bound of the tuning space[cite: 1].

Fixing the tuning harness and LDS allocations

The tune_gemm_tile.py script acts as an automated test harness that patches benchmark.go to sweep through square local work-group dimensions[cite: 1]. Deploying this required correcting a CLI flag mismatch and making the Local Data Share (LDS) allocation dynamically match the tile scale[cite: 1].

Correction 1 · CLI Flag Mismatch

The Python script originally passed -num-gpu={args.gpus}, but the benchmark runner only accepts an explicit list of GPUs[cite: 1]. This was patched in the command builder array[cite: 1]:

# tune_gemm_tile.py: runtime execution arguments cmd = [ binary, "-timing", "--report-all", f"-gpus=1,2", # Explicit comma-separated list fix f"-m={args.m}", f"-k={args.k}", f"-n={args.n}", f"-algorithm={args.algorithm}", ] + args.extra

Correction 2 · Dynamic BlockA LDS Allocation

The original Go kernel hardcoded the LDS allocation for the A matrix tile to 4KB (32 * 32 * 4 bytes), valid only for tileSize=8[cite: 1]. At tileSize=16, the kernel requires 16KB[cite: 1]. The Python regex seamlessly handles this patch, and the change has been permanently merged into the Go source[cite: 1]:

// benchmark.go: matrixmultiplication.KernelArgs kernArgs := &matrixmultiplication.KernelArgs{ MatrixA: gAs[g] + driver.Ptr(aOffset), MatrixB: gBs[g], MatrixC: partialC[g] + driver.Ptr(cOffset), WidthA: kSlice, BlockA: (4 * tileSize) * (4 * tileSize) * 4, // Dynamically scaled }

The Confounder: Tile Size dictating Launch Count

A critical observation in benchmark.go is that the number of output rows computed per kernel launch is directly tied to the tile size[cite: 1]:

// benchmark.go: launch dimensions const tileSize = 8 const rowBand = 4 * tileSize // Launch count scales with tileSize

Because of a known kernel offset bug in the simulator's Y-dimension logic, the benchmark launches one workgroup-row per kernel call[cite: 1]. This means changing tileSize simultaneously alters the kernel launch count[cite: 1]. For tileSize=4, the driver issues 16 launches; for tileSize=16, it issues just 4[cite: 1]. The sweep results are therefore partially measuring the amortization of Driver dispatch overhead[cite: 1].

Memory latency bounds and register constraints

Memory Stalls at Small Tiles

The detailed CSV metrics for tileSize=4 reveal heavy stalling within the Compute Units (CUs)[cite: 1]. Across GPU 1, the SIMD CPI averages 43.07 and the overall CU CPI averages 36.03[cite: 1]. This exceptionally high cycle-per-instruction rate indicates that the 4×4 work-groups are heavily memory-bound, failing to amortize global memory access latencies over their small local memory allocations[cite: 1].

Register Constraints Cap the Tuning Space

While larger tiles perform better, the tuning script actively prevents arbitrary scaling[cite: 1]:

# tune_gemm_tile.py: constraints if tile * tile > 256: return False, f"{tile}x{tile}={tile*tile} work-items exceeds the conservative 256-thread limit"

This guard prevents a silent MGPUSim hang[cite: 1]. A 32×32 work-group (1024 items, or 16 wavefronts) would exceed the maximum hardware capacity of 12 wavefronts per CU, a limit dictated by this specific kernel's 74 VGPR usage[cite: 1].
