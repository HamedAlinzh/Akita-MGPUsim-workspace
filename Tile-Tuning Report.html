Technical Note: GEMM Tile Tuning & Simulator Validity

Evaluation of the tune_gemm_tile.py tuning script: Integration bug fixes, experimental validity caveats, and empirical sweep analysis.

Author: Hamed Alinezhad

Thank you for the feedback—you are entirely correct that the GEMM tile size was previously untuned.

The default 8×8 workgroup configuration was inherited directly from the original AMD APP SDK sample launch setup, making the 32×32 output tile an inherited default rather than an optimized design choice. Making tile size a tunable parameter is clearly the correct approach.

Your catch regarding BlockA was both accurate and critical. BlockA specifies the Local Data Share (LDS) allocation for the A matrix tile. Hardcoded at 32 * 32 * 4 bytes, it is valid only for tileSize=8. At tileSize=16, the kernel requires 16 KB rather than 4 KB; sweeping without this correction would produce incorrect numerical results rather than merely suboptimal performance. I have permanently integrated the dynamic allocation formula (4 * tileSize) * (4 * tileSize) * 4 into the codebase.

All host changes and simulator workspace updates are pushed and accessible in the repository: Akita-MGPUsim-workspace.

Script Execution & Integration Issues

Before running the sweep, two execution issues in the script required resolution:

  1. CLI Flag Mismatch: The tuning script invokes -num-gpu=2, but the benchmark runner expects a explicit comma-separated list via -gpus=1,2. Consequently, every tile run exited prematurely with code 2 prior to simulation.
  2. Fragile String Matching: The script's guard check for an existing BlockA patch performs a literal string comparison containing a single space (BlockA: ...). However, gofmt automatically formats struct fields with two spaces to align with the adjacent MatrixA: key. Because the script inserts one space and then runs gofmt -w, its own patch fails the guard check on subsequent runs, limiting execution to unpatched source files.

Experimental Validity & Architectural Findings

To ensure tile rankings reflect true architectural efficiency, three major experimental caveats must be addressed:

1. The Sweep Confounders: Tile Size vs. Launch Count

In the benchmark implementation, rowBand = 4 * tileSize. As a result, changing tileSize simultaneously alters the kernel launch count and the number of active workgroups. For a 256³ GEMM on 2 GPUs:

tileSize Output Tile Launches / GPU Concurrent WGs Busy CUs (out of 64)
416×16161625.0%
832×328812.5%
1664×64446.25%

Consequently, any performance ranking measures a tradeoff between launch overhead and Compute Unit (CU) occupancy, rather than pure tiling efficiency. The root cause is a row-offset handling bug in the reused kernel, forcing a launch loop that dispatches one workgroup-row per iteration. Fixing this kernel offset bug to decouple tile size from launch count is a prerequisite for a clean tile study.

2. Unmodeled LDS Occupancy in MGPUSim

MGPUSim's resource allocation path inspects co.WGGroupSegmentByteSize, which evaluates to 0 for this kernel. Therefore, the 16 KB LDS allocation requested by tileSize=16 incurs zero occupancy cost in simulation. On physical hardware, requiring 16 KB of LDS would cap CU occupancy at 4 workgroups per CU. As it stands, the simulator sweep is systematically biased toward larger tiles.

3. Register Constraints Cap the Feasible Search Space

A setting of tileSize=32 represents 1024 work-items (16 wavefronts). However, given the kernel's demand of 74 VGPRs per work-item, a CU can accommodate at most 12 wavefronts:

16384 registers / SIMD ÷ 4 (granularity) ÷ 64 (lanes) = 64 units
ceil(74 / 4) = 19 units needed per wavefront
floor(64 / 19) = 3 wavefronts / SIMD × 4 SIMDs = 12 wavefronts / CU max

Because a 16-wavefront workgroup exceeds the physical CU register capacity, MGPUSim hangs indefinitely waiting for resources rather than reporting an allocation error. Thus, the actual feasible search space is restricted to {4, 8, 16}. The script's 256-workgroup-thread guard incidentally prevents this hang.

Empirical Sweep Results

Following the flag and execution fixes, the sweep was executed for a 256³ GEMM workload across 2 GPUs using the Ring All-Reduce algorithm.

Simulated execution times in microseconds (μs). Non-kernel overhead = total_time − kernel_time.
tileSize Output Tile Launches / GPU Total Time (μs) Kernel Time (μs) Non-Kernel Overhead (μs) Relative Speedup
4 16×16 16 1653.2 687.4 965.8 2.327×
8 32×32 8 1013.3 412.6 600.7 1.426×
16 64×64 4 710.4 292.1 418.2 1.000× (Best)
Key Takeaway

The empirical results confirm the confounding effect described above: reducing the launch count by 4x reduces total time, kernel time, and driver overhead proportionally (~2.33x). Because the total work-item count remains identical across all three runs, and tileSize=16 leaves 93.75% of CUs idle (utilizing only 4 out of 64 CUs), the speedup reflects launch overhead amortization rather than intrinsic tiling efficiency.

Metric note: kernel_time includes the Push and Reduce kernels associated with All-Reduce because they are dispatched via LaunchKernel. The non-kernel metric captures driver dispatch overhead, host orchestration, and command queue flushing.

Summary & Recommended Next Steps

Optimizing end-to-end execution time (GEMM computation coupled with All-Reduce communication) is the correct objective, and the FlashOverlap / TileLink framework aligns well with this model.

Proposed Action Items:

  1. Fix the kernel's row-offset calculation bug to decouple tile dimensions from launch counts.
  2. Patch MGPUSim's LDS accounting path so that dynamic LDS allocations properly constrain CU occupancy.
  3. Proceed to second-stage tuning (tuning TILEX/TILEY micro-tiles and recompiling HSACO binaries via clang-ocl) only after the simulator accurately enforces LDS allocation costs.
